# KittenTTS 独立语音服务设计文档

## 目标

为银龄智伴增加一个稳定、可控的文本转语音能力，解决浏览器原生 Web Speech 在自动播放限制、浏览器兼容性和声音一致性上的不稳定问题。方案采用独立 Python TTS 服务，而不是把语音推理塞进现有 Cloudflare Pages Functions。

## 为什么不继续只依赖浏览器语音

当前前端已经接入了 Web 语音桥接，但实际用户体验仍然不稳定，根因通常包括：

- 浏览器自动播放策略拦截
- 不同浏览器对 `speechSynthesis` 支持不一致
- 声音质量、语速和可用音色不可控
- 线上环境中即使“调用成功”，也不等于用户真的能听到声音

因此继续只修浏览器语音并不能从根本上解决产品层面的可用性问题。

## 设计方案

采用“双轨语音”方案：

1. **主路径：独立 TTS 服务**
   - 使用 `KittenTTS`
   - 用 Python + FastAPI 封装 `POST /tts`
   - 部署到 Railway
   - 前端拿到音频后直接播放

2. **回退路径：浏览器 Web Speech**
   - 当独立 TTS 服务失败或不可达时，回退到现有 `WebSpeechService`
   - 保留手动重播按钮
   - 不让聊天主流程被语音失败阻断

## 服务架构

### 部署形态

- 独立于 `Silver-Companion-AI` 前端站点部署
- 使用 Railway 托管 Python Web 服务
- 不放在 Cloudflare Pages Functions 中运行

### 服务接口

建议接口：

`POST /tts`

请求体：

```json
{
  "text": "您好，今天感觉怎么样？",
  "voice": "Bella",
  "speed": 1.0
}
```

响应：

- `audio/wav`（首版推荐）

首版不要求做用户鉴权，但应限制输入长度，避免被滥用。

## KittenTTS 选型

依据 KittenTTS 官方说明：

- 基于 Python + ONNX
- 可在 CPU 上运行
- 有多个模型尺寸
- 适合做轻量独立推理服务

首版建议：

- 从较小模型开始，优先追求“能跑通、延迟可接受、部署稳定”
- 先固定一个默认 voice，避免一开始把问题扩展到音色管理

## 前端接入设计

### 聊天页行为

- AI 回复成功后，前端优先请求 TTS 服务
- 如果请求成功：
  - 获取音频 blob
  - 通过 `audio` / `AudioElement` 播放
- 如果请求失败：
  - 回退到当前 `WebSpeechService.speak()`

### 播放控制

- 保留现有语音开关
- 保留每条 AI 回复的重播按钮
- 对用户而言，不需要关心当前走的是服务端 TTS 还是浏览器回退

## 配置设计

前端新增环境变量，例如：

- `TTS_API_BASE_URL`

如果未配置该值：

- 默认不启用独立 TTS 服务
- 自动回退到当前浏览器语音方案

## 安全与稳定性

首版建议至少做：

- 限制文本长度
- 请求超时
- 基础错误日志
- 避免把完整异常原文暴露给前端

后续可增加：

- 简单鉴权
- Rate limit
- 结果缓存

## 测试策略

- Python 服务侧：
  - 接口单测
  - 长度校验
  - 空文本校验
- Flutter 前端侧：
  - TTS 客户端请求成功时播放音频
  - TTS 失败时回退到 `WebSpeechService`
  - 保持聊天主流程不受语音失败影响

## 不在范围内

- 移动端原生 TTS SDK
- 多语音包切换 UI
- 用户自定义音色
- 音频缓存/CDN 优化
