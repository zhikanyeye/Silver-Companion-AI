# 银龄智伴第二轮精修与语音播放设计文档

## 目标

在现有第一轮全站统一和核心功能闭环基础上，继续做第二轮产品精修：让首页、老人端、子女端、聊天页在视觉层级和交互细节上更一致，同时补齐 AI 回复语音播放能力，使聊天体验从“可用”进一步提升到“更像正式产品”。

## 范围

- 首页（`landing_page.dart`）
- 品牌主视觉（`brand_hero.dart`）
- 老人端首页与活动页
- 子女端首页
- 聊天页与语音播放交互
- Web 语音播放调用链

## 第二轮精修方向

### 首页

- 顶部登录 / 注册入口从简单按钮组提升为更完整的品牌入口条
- 强化首屏视觉秩序，让顶部动作区与 `BrandHero` 更像一个整体
- 优化背景层次、内边距和模块呼吸感，减少“只有主卡漂亮”的断裂感

### 老人端

- 顶部服务大厅 hero 增加更强的“今日重点”表达
- `AI陪伴`、`一键求助`、`活动` 三项高频入口进一步拉开主次
- 求助弹层和活动页卡片继续向统一服务页语言靠拢

### 子女端

- 让顶部总览卡更像真正的“总览面板”，而不是几个并排指标容器
- 强化状态区与提醒区的关系和密度
- 让加载态、刷新态、失败态与聊天 / 设置页状态风格更一致

### 聊天页

- 进一步统一头部、提示条、消息气泡、输入区、加载条的细节
- 加入语音播放相关的显式控制，不再只依赖内部自动调用

## 语音播放设计

### 交互模式

采用“自动播报 + 手动重播”的混合方案：

- AI 回复到达后，尝试自动播报
- 每条 AI 消息增加一个播放 / 重播按钮
- 在聊天页加入一个播报开关，用于启用或关闭自动播报

### 失败回退

考虑浏览器自动播放限制和兼容性问题：

- 如果自动播报被浏览器策略拦截，不中断聊天主流程
- 页面保留手动播放按钮，用户仍可主动触发播报
- 对于不可用场景，应提供轻量提示，而不是静默失败

### 技术判断

当前 `ChatController.sendText()` 已调用 `_speechService.speak(reply)`，说明问题不在“完全没有接线”，而更可能在以下几层：

- Web 语音桥接没有真正执行
- 浏览器环境下 `speechSynthesis` 调用没有成功
- 自动播放被浏览器策略限制
- 页面没有可见的手动重播入口，导致用户感知为“没有语音功能”

因此本轮不只是补 UI，还要补“可见控制 + 回退路径 + 基础可用性验证”。

## 测试策略

  - 播报开关可见
  - AI 消息带播放按钮
  - 点击按钮会调用语音服务
- 保留首页 / 老人端 / 子女端原有结构测试
- 视需要增加少量页面结构回归测试，确保第二轮精修不破坏主流程
- 完成后运行相关 targeted tests，再跑全量 `flutter test`

- 做音色选择、语速调节等高级语音设置
- 引入全新导航系统
- 重写聊天核心逻辑
